# Prompt Engineering 기록

이 문서는 프로젝트 개발 과정에서 생성된 문서들과 그 효과를 기록합니다.

## 문서 생성 과정

### 1. README.md 생성
**질의**: "프로젝트 개요를 설명하는 문서를 작성하려고 해"

**생성 내용**:
- 프로젝트 소개
- 주요 기능 설명
- 사용 방법
- 향후 계획

**효과**:
- 프로젝트의 전체적인 목적과 기능을 명확히 정의
- 개발 방향성 설정
- 향후 협업자나 사용자를 위한 가이드 제공

### 2. specification.md 생성
**질의**: "README.md와 constitution.md를 참고해서 specification.md에 정의할 스펙들을 기술해볼래"

**참고 문서**:
- `README.md`: 프로젝트 개요 및 주요 기능
- `constitution.md`: 프로젝트 제약사항 및 성공 기준

**생성 내용**:
- 기능 요구사항 (FR-001 ~ FR-019)
- 비기능 요구사항 (NFR-001 ~ NFR-012)
- UI/UX 요구사항 (UI-001 ~ UI-008)
- 기술 요구사항 (TECH-001 ~ TECH-006)
- 제약사항 (CONST-001 ~ CONST-005)

**효과**:
- 각 기능에 고유 ID 부여로 추적 가능
- 명확한 요구사항 정의로 개발 방향 명확화
- 테스트 및 검증 기준 제공
- 개발 중 요구사항 변경 시 추적 용이

### 3. plan.md 생성
**질의**: "README.md, specification.md, constitution.md를 참고해서 사용할 기술스택과 어떤 구조로 개발할 건지를 plan.md 파일에 작성해줘"

**참고 문서**:
- `README.md`: 프로젝트 개요
- `specification.md`: 기능 및 기술 요구사항
- `constitution.md`: 제약사항 (비용, 시간, 인력)

**생성 내용**:
- 기술 스택 선택 및 이유
- 프로젝트 구조
- 개발 단계별 계획 (Phase 1 ~ 7)
- 주요 기술 결정 사항
- 예상 비용 및 일정

**효과**:
- 기술 스택 선택의 명확한 근거 제공
- 단계별 개발 계획으로 진행 상황 추적 가능
- 제약사항을 고려한 현실적인 계획 수립
- 개발 중 참고 자료로 활용

### 4. .cursor/rules/rule.md 생성
**질의**: "rules에 rule을 정의하면 될거같은데. 구현할 때, 어떤 걸 참고해야 하는지, 어떤 걸 유의해야 하는지를 specification.md, constitution.md를 보고 추가하자"

**참고 문서**:
- `specification.md`: 기능 요구사항, 비기능 요구사항
- `constitution.md`: 프로젝트 제약사항

**생성 내용**:
- 프로젝트 개요 및 핵심 원칙
- 제약사항 (비용, 시간, 인력, 트래픽)
- 기술 스택 규칙 (필수 사용, 금지 사항)
- 코드 작성 규칙
- 기능 구현 규칙
- 성능 요구사항
- UI/UX 요구사항
- 에러 처리 규칙
- 구현 우선순위

**효과**:
- **AI 어시스턴트가 코드 작성 시 자동으로 참고**
- 일관된 코드 스타일 유지
- 제약사항 준수 (비용, 시간, 인력)
- 기술 스택 선택의 일관성 유지
- 불필요한 라이브러리 추가 방지
- 개발 방향성 유지

## 문서 간 관계

```
constitution.md (제약사항)
    ↓
README.md (프로젝트 개요)
    ↓
specification.md (상세 요구사항)
    ↓
plan.md (기술 스택 및 개발 계획)
    ↓
.cursor/rules/rule.md (AI 구현 규칙)
```

## 문서 활용 효과

### 1. 개발 일관성
- 모든 문서가 동일한 제약사항과 목표를 공유
- 기술 스택 선택의 일관성 유지
- 코드 스타일 통일

### 2. 개발 효율성
- AI 어시스턴트가 `.cursor/rules/rule.md`를 자동 참고
- 불필요한 질문 감소
- 올바른 기술 선택 자동화

### 3. 제약사항 준수
- 비용 제약 ($5 이하) 자동 고려
- 시간 제약 (1주 이내) 반영
- 인력 제약 (1명) 고려한 단순 구조 유지

### 4. 품질 보장
- 명확한 요구사항 정의로 누락 방지
- 테스트 기준 제공
- 성능 요구사항 준수

## 실제 활용 사례

### 사례 1: 기술 스택 선택
**상황**: Next.js vs React + Vite 선택
**참고 문서**: `plan.md`, `.cursor/rules/rule.md`
**결과**: 
- Next.js는 과함 (SSR/SSG 불필요)
- React + Vite 선택 (가벼움, 운영 비용 0)
- 제약사항 준수 (비용, 시간)

### 사례 2: 라이브러리 선택
**상황**: 상태 관리 라이브러리 선택
**참고 문서**: `.cursor/rules/rule.md`
**결과**:
- Redux, Zustand 사용 금지
- Context API + useReducer 사용
- 제약사항 준수 (단순 구조, 추가 라이브러리 지양)

### 사례 3: API 선택
**상황**: 카카오맵 API vs 네이버지도 API
**참고 문서**: `plan.md`, `specification.md`
**결과**:
- 카카오맵 API 선택 (무료 티어 충분)
- 제약사항 준수 (비용 $0)

### 사례 4: 배포 플랫폼 선택
**상황**: 호스팅 플랫폼 선택
**참고 문서**: `plan.md`, `.cursor/rules/rule.md`
**결과**:
- GitHub Pages 선택 (완전 무료)
- 제약사항 준수 (비용 $0)

## 문서 작성 원칙

### 1. 단계적 구체화
1. **constitution.md**: 제약사항 정의 (최상위)
2. **README.md**: 프로젝트 개요 (일반적)
3. **specification.md**: 상세 요구사항 (구체적)
4. **plan.md**: 기술 스택 및 계획 (실행)
5. **rule.md**: AI 구현 규칙 (실행 가이드)

### 2. 상호 참조
- 각 문서가 다른 문서를 참고
- 일관성 유지
- 중복 최소화

### 3. ID 체계
- 요구사항에 고유 ID 부여 (FR-001, NFR-001 등)
- 추적 및 관리 용이
- 변경 이력 관리 가능

## AI 어시스턴트 활용 효과

### 자동 참고
- `.cursor/rules/rule.md`는 Cursor IDE가 자동으로 읽음
- 코드 작성 시 규칙 자동 적용
- 제약사항 자동 준수

### 일관성 유지
- 모든 코드가 동일한 규칙 적용
- 기술 스택 선택의 일관성
- 코드 스타일 통일

### 효율성 향상
- 불필요한 질문 감소
- 올바른 선택 자동화
- 개발 속도 향상

## 결론

문서화를 통해:
1. **명확한 목표 설정**: constitution.md로 제약사항 정의
2. **상세한 요구사항**: specification.md로 기능 정의
3. **실행 계획**: plan.md로 기술 스택 및 계획 수립
4. **AI 가이드**: rule.md로 AI 어시스턴트가 자동 참고

이러한 문서화는:
- 개발 일관성 유지
- 제약사항 준수
- 개발 효율성 향상
- 품질 보장

에 큰 효과를 발휘했습니다.
